# Upgrading to EntropicMem 3.0 — the drill report

**EM-901's deliverable.** Every claim below is exercised by a drill that runs in
the normal suite (`tests/unit/test_em901_upgrade_drills.py`), so this page
cannot silently rot: if an upgrade path breaks, a drill goes red.

**Who this is for:** an existing user on the released line (`v2.8.1`, what the
Hermes catalog pins) deciding whether to take the 3.0 update, and anyone
migrating a v2 store to the v3 engine.

## The one-paragraph answer

Updating the plugin does not touch your data. The 3.0 provider detects the
store's schema version and keeps serving a v2 store with the v2 engine — the
same behavior, the same files, no migration. The v3 engine (semantic recall,
the vault projection, the graph, episodes, formation) activates only after a
deliberate, backed-up migration you run yourself. New capabilities ship
switched off (`vault.projection: none`, `vault.ingest_human_edits: false`,
`formation.mode: off`), so nothing writes anywhere without your asking.

## What the drills drive, and what they prove

The committed fixture stores (`tests/fixtures/db/`) were generated by running
the **real v2.3.0 / v2.5.0 / v2.7.0 engines** against synthetic data
(`generate_fixtures.py`; the v2.5 and v2.7 releases share a schema, and their
fixtures are byte-identical). The 2.8.1 generation is derived honestly: a 2.7
store opened once by the 2.8 engine, whose idempotent column ladder is exactly
what a real 2.8.1 store is. A fifth, rich fixture exercises the migration's
recorded edge cases (duplicate content, orphans, unparseable timestamps,
`facts_archive`, tables 3.0 does not model).

| Drill | Proves |
|---|---|
| Migrate 2.3 / 2.5 / 2.7 / 2.8.1 → 3.0 | All five migrations apply; `user_version` reaches the latest; `integrity_check` stays `ok`. |
| Nothing lost | Every v2 fact resolves by its legacy id with byte-identical content; deleted rows land `deleted`; pending rows land `pending`; episode and version-snapshot counts survive. |
| The store serves | `MemoryStore.get` resolves each v2 fact id through the v3 read path's own legacy-id form. |
| The vault | An old-style vault (the 2.8 writer's quoted-unescaped titles, a `---` horizontal rule in a body) with a legacy index migrates to the current index generation and serves search and a graph export. |
| Sync 2.8 → 3.0 | A capsule exported from a 2.8.1 profile imports into a 3.0 profile and migrates cleanly there. |
| Sync 3.0 → 2.8 | Pinned limitation — see below. |
| The evidence is safe | The committed fixtures are hash-pinned; the drills copy, never write. |

## What a 2.8.1 user loses or changes by updating

- **On a store you have not migrated:** `update`, `entity`, and `review`'s
  restore/feedback actions answer `needs_v3_store`. Remember, search, forget
  and stats keep working. Nothing is lost — the features are waiting on the
  migration.
- **Tool names:** the legacy tool names (`entropicmem_recall`, `_query`,
  `_get`, `_patch_core`, `_consolidate`) route to the new surface for one
  minor version and report `deprecated_tool`. The mapping is:
  `_recall`/`_query`/`_get` → `entropicmem_search`, `_patch_core` →
  **`entropicmem_profile`** (`action="patch"`), `_consolidate` →
  `entropicmem_review` (`action="consolidate_preview"` — the tool only ever
  previews; running a real consolidation stays CLI-only, by design). The
  previously planned name `entropicmem_patch_core_memory` never existed.
- **The system prompt is rebuilt** (policy text, conditional tool bullets, an
  800-token core budget) — model behavior can shift subtly.
- **The remember surface tightened:** the v2 remember forced
  `domain=Knowledge` and no sensitivity; the v3 schema takes explicit values
  (a migrated row keeps what it had — new writes say what they mean).
- **Writes are injection-screened** (fail-open; flagged content keeps a
  warning marker), and forget confirmations are now random single-use tokens.
- **The host floor is real:** 3.0 requires `hermes-agent >= 0.21.3` and
  Python >= 3.10. Windows support improves (native Windows is unsupported on
  2.8.x).
- **Catalog installs pull no new dependencies** (the engine is stdlib-only);
  pip installs resolve the optional extras by the manifest's floors, which
  state the minimum that is verified — never a version above what CI tests.

## Sync between a 2.8 profile and a 3.0 profile

- **2.8 → 3.0 works:** export a capsule on the old profile
  (`entropicmem export`), import it on the 3.0 profile
  (`entropicmem import --trust-unverified` — capsules prove integrity, not
  origin), then migrate the imported store normally. The drill drives exactly
  this and verifies every row lands. The import refuses a store newer than
  the build and takes a verified backup of the target before replacing it —
  the drills pin both.
- **3.0 → 2.8 requires both upgraded.** The migration renames the v2 tables
  (`v2_facts`, …) inside the migrated store, so a 2.8 engine opening a
  migrated store sees an **empty** `facts` table — the drill pins this so the
  behavior cannot change silently. Sync a migrated store only to profiles on
  3.0.

## Migrating a v2 store to the v3 engine

1. Back up (the migration also takes its own verified pre-migration backup
   automatically).
2. Run the store migrator with the explicit opt-in — the runner refuses
   anything that is not a temp/test path otherwise, so the flag is the
   deliberate act:

   ```
   ENTROPICMEM_ALLOW_LIVE_MIGRATION=1 python -c \
     "from em.store.db import open_db; from em.store.migrations import migrate; \
      conn = open_db('memory.db'); migrate(conn); conn.close()"
   ```

   (run inside the plugin's `scripts/` directory, against a **copy first** —
   the drills are exactly that, run every CI push)
3. Re-opening a migrated store needs no env var: the migration runner's
   path guard runs only when a migration would actually run (a drill pins
   it), so the opt-in is the one-time act it was meant to be. Creating a
   fresh store needs no env var either (an empty store has nothing the guard
   protects).
4. Note the CLI's existing `migrate` command is **not** this: it is the v2-only
   P1 provenance migration and refuses on a v3 store. A friendly
   `entropicmem memory upgrade` command wrapping the real migrator is a
   recorded gap for the release checklist.
4. The drill report is the evidence this is safe for real stores: the data
   move is lossless (renames, not drops), duplicates are superseded rather
   than deleted, orphan rows are preserved in the `v2_*` tables, and the audit
   chain is rebuilt with every detail value preserved.

## Known gaps

- There is **no `doctor` command yet** (the drills verify integrity, counts,
  legacy-id resolution and the served path directly). A `doctor` that wraps
  those checks is a recorded candidate for the release checklist.
- There is **no friendly cutover command** — the store migrator is a library
  call (the snippet above); wrapping it as `entropicmem memory upgrade` is a
  recorded gap for the release checklist.
- The eval parity half of the drill is the engine-parity suite
  (`tests/parity/test_engine_parity.py`), which pins the v2 and v3 engines to
  the same behaviors; the drills add the migrated-data parity (pre-migration
  answers are findable post-migration).

## The old-vault bug the drills found (fixed)

The drill's first run **caught a real upgrade break**: a 2.8 vault writes
`tags: ` (YAML-null) for every note without tags, and the new frontmatter
reader handed that null to `Note.importance`, which died on `len(None)` — the
3.0 index rebuild would have crashed on exactly the vaults real users have.
The read boundary now coerces null → `[]` and comma strings → lists (what the
old reader did), and the drill pins it. Without EM-901 this would have shipped
in the release.
