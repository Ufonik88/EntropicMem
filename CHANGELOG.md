# Changelog

All notable changes to EntropicMem are documented here. The format follows Keep a Changelog.

## [Unreleased]

### Security

- **Private identifier denylist (privacy guard v2).** The privacy guard no longer ships any identifier list, not even as SHA-256 digests: unsalted hashes of short words (names, a company, a bank) are reversible with a word list, so a public hash list republished what it was meant to protect. Digests now come from the `ENTROPICMEM_PRIVACY_DIGESTS` Actions secret (CI) or a local file (`~/.config/entropicmem/privacy-digests.txt`); where secrets exist CI sets `ENTROPICMEM_REQUIRE_PRIVACY_DIGESTS=1`, so a missing list fails instead of skipping. Failure output names file, line and list position only, never the word (CI logs are public). The scan now also reads fixture databases (`.db`/`.sqlite`) as raw bytes, and a test fails if a digest list is committed again. The phone-number rule stays public.
- **Identity guard fails closed.** `scripts/check_commit_identity.sh` no longer swallows `git rev-list` errors (an unresolvable range used to report "nothing to check" and pass); on push it now checks the whole history reachable from the pushed commit, which also covers force-pushes.

### Added

- **EM-204: migration `0002_v3_core` — the v3 schema and the lossless move of every v2 row into it.** Creates the v3 tables (`memories`, `relations`, `entities`, `episodes`, `jobs`, `audit_log`, `meta`, plus external-content `memories_fts`/`episodes_fts` with their sync triggers), renames each v2 source table to `v2_<name>` and keeps it for one release, then copies the data across with new type-prefixed ULIDs while remembering the old id in `legacy_id`. The original ids stay readable: the migration never commits, and a fresh v2 store ends up on `user_version=2` with all v3 tables.
- **EM-204: in-migration parity verification that aborts rather than migrates quietly.** After the data move the migration re-derives expected counts from the renamed v2 tables and compares them per table; it also recomputes `content_hash` for every moved memory, recomputes the audit chain hash for every row, and probes both FTS indexes. Any mismatch raises `ParityError` inside the migration transaction, so the runner rolls the whole thing back and the database stays at its previous version. Seven independent mutations (drop a row, corrupt content, break the chain, drop an FTS trigger, skip dedup, skip episodes, tamper a stored audit row) were each confirmed to be caught, rather than assumed to be.
- **EM-204: v2 rows that v3 cannot represent are preserved, not dropped.** Orphaned `embeddings` and `fact_versions` rows (rows whose parent no longer exists — the real store has 6 and 40) stay in the `v2_*` tables and their counts are recorded in `meta` as `orphans_*`, so the parity arithmetic still balances to the exact v2 row count. Nothing is deleted and nothing dangles under `foreign_keys=ON`.
- **EM-204: rich synthetic v2 fixture builder** (`tests/fixtures/db/build_rich_v2.py`). The committed v2 fixtures hold only two rows, which is far too little to exercise dedup, episodes, archives, orphaned children or the timestamp shapes the real store actually contains, so the builder reconstructs a v2.7 database with all of them from `0001`'s exact schema. It deliberately opens with `foreign_keys=OFF`, because that is how v2 runs and is the only reason orphaned rows can exist in a real store at all — a builder that enforced foreign keys could not reproduce the condition the migration has to survive.

- **EM-203: migration framework — `em/store/migrations/`.** Each migration is a module named `NNNN_<slug>.py` exposing `VERSION: int`, `NAME: str` and `def up(conn)`. `discover()` loads every numbered module in version order and rejects malformed modules, duplicate versions and gaps in the numbering (migrations must be contiguous from 1, otherwise `user_version` stops meaning "everything up to N has been applied"). `migrate()` backs the database up first via the SQLite backup API to `backups/pre-migrate-v{from}-to-{to}-<ts>.db` (0600, consistent even with a live WAL), then applies each pending migration in its **own** transaction together with its `schema_migrations` row and the `PRAGMA user_version` bump, so a failure mid-migration leaves the database exactly at the last good version. Re-running is a no-op and writes no extra backup; a partially migrated database resumes at the next version instead of re-applying. A database newer than the build raises `DowngradeError`. Editing an already-applied migration raises `MigrationChecksumMismatch` (the recorded `checksum` is `sha256` of the module source) rather than being silently treated as applied.
- **EM-203: development safety guard — migrations refuse to touch a live database.** `assert_safe_db_path()` resolves the path (so `.../entropicmem/../entropicmem/memory.db` cannot dodge the check) and raises `MigrationRefused` for anything outside a temporary or test location; `~/.hermes/entropicmem` and `~/.hermes/entropicmem-live-2.8.0` are denied outright. In-memory databases are always allowed. `migrate()` runs the guard *before* opening a backup or writing anything, so a refused database is not touched at all. The real 3.0 cutover opts in with `ENTROPICMEM_ALLOW_LIVE_MIGRATION=1`, which nothing in development or CI sets.
- **EM-203: migration `0001_baseline_v27`** — the frozen copy of v2's `MemoryEngine._init_schema()` that brings any v2.x store (or an empty database) to the exact v2.7 shape. Every statement is `IF NOT EXISTS` or guarded by a `PRAGMA table_info` check, so it is idempotent across v2.3/v2.5/v2.7/v2.8. `up()` never commits (the runner owns transaction boundaries; `executescript` is deliberately avoided because it issues an implicit COMMIT that would break atomicity). Faithfulness was verified against the real historical engines rather than by reading source: `embeddings` is created unconditionally (v2 gated it on optional deps, but EM-204 moves its rows), `facts_archive` is only *upgraded*, never invented, and `SHARED_SCHEMA` is excluded because it belongs to the separate shared store.
- **EM-203: committed v2.x migration fixtures** (`tests/fixtures/db/v2_{3,5,7}_0.db`) plus `generate_fixtures.py`, which extracts each release commit with `git archive` and runs that release's **real** `MemoryEngine` against a fresh database. An earlier regex-scraping version of the generator was measurably wrong — it emitted `embeddings` and `facts_archive` tables that real v2.7.0 code does not create — so the generator executes the historical code instead of approximating it. Fixtures are ~25-32 KB, contain exactly two clearly synthetic rows, and are committed so CI needs neither git history nor the historical imports.
- **EM-202: portable storage core — `em/store/` (`db.py`, `locking.py`).** `open_db()` is the single connection factory for the v3 core: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`, `temp_store=MEMORY`, `mmap_size=64MiB`, `isolation_level=None` (explicit transactions only), readonly connections via the SQLite URI `mode=ro`, POSIX perms 0600 file / 0700 dir. `write_txn()` is a `BEGIN IMMEDIATE` … `COMMIT`/`ROLLBACK` context manager with up to 3 jittered retries on SQLITE_BUSY — **no advisory file locks**: cross-process serialisation is SQLite's (BEGIN IMMEDIATE + busy_timeout), proven by the card's concurrency AC (4 writer processes × 500 writes + 1 reader: zero errors, all 2000 rows, reader p95 < 50 ms). `migration_lock()` guards what SQLite cannot see: an `O_CREAT|O_EXCL` lock file (portable, no fcntl/msvcrt), stale after 10 minutes. `ensure_schema()` implements the `PRAGMA user_version` fast path (== LATEST skips all DDL) and refuses DBs newer than the code (`DowngradeError`). `Store` keeps per-thread reader connections (`threading.local`) and ONE process-wide writer serialised by a `threading.Lock`. Stdlib-only, no Hermes imports, no env reads.
- **EM-201: `em/` package scaffold + clock & ULID identifiers** (`plugins/entropicmem/scripts/em/`). `em.clock` is the single source of time truth for the v3 storage core: `utc_now()` (freezable via `em.clock.freeze(dt)` for tests/evals), `to_iso()` (UTC, millisecond precision, `Z` suffix), `parse_iso()` (accepts the v3 canonical form plus the legacy shapes the v2 engine wrote — SQLite `CURRENT_TIMESTAMP` space-separated, `+00:00` and arbitrary offsets, naive-as-UTC), `new_id(prefix)` (type-prefixed ULID: 48-bit ms timestamp + 80 random bits, Crockford base32, sorts chronologically) and `short_id()` (last 8 chars, the citation form). Stdlib-only, no Hermes imports, no environment reads. 41 unit tests including the AC property test (`parse_iso(to_iso(x)) == x` at ms precision) and ULID sort order; mutation-checked.

### Changed

- **EM-203: `pyproject.toml` packages `em.store.migrations`** alongside `em` and `em.store` (the same silent-omission bug EM-202 hit one level up: without it the migration modules would be missing from the wheel).
- **EM-203: `db.LATEST_USER_VERSION` now resolves lazily from the migration registry** via `resolve_latest_user_version()`, which `ensure_schema()` calls. The registry lives in a module that depends on `db`, so `db` could only pick the value up as an import side effect — importing `em.store.db` on its own left it at 0 and `ensure_schema` would then reject any already-migrated database as a "downgrade". The lazy import avoids that without creating a circular import. Pinned by a test that runs in a fresh interpreter and asserts `em.store.migrations` was never imported.
- **EM-203: `.gitignore` no longer swallows the committed migration fixtures** (`!tests/fixtures/db/*.db`). The blanket `*.db` rule would have silently excluded them, and because the tests skipped on a missing fixture the card's main acceptance criterion would have gone vacuous in CI rather than failing. The migration tests now hard-fail on a missing fixture, and assert every fixture contains only the two clearly synthetic rows.
- **EM-202: Windows is a supported platform — the v2 engine and CLI no longer import platform lock modules.** `memory_engine.py` dropped its top-level `import fcntl` (the exact line that made `import memory_engine` fail on Windows) and the CLI's `_provider_running()` dropped its inline fcntl probe; both now use `em.store.locking.FileLock` (fcntl on POSIX, `msvcrt.locking` byte-range on Windows, identical semantics, interoperating with locks taken by older builds). The engine's reentrant write-lock counter is unchanged. A drift-guard test fails if a direct `fcntl`/`msvcrt` import grows back outside `em/store/locking.py`. The CI `windows-import` job loses `continue-on-error` and now runs the store test suite on windows-latest.
- **EM-202: `pyproject.toml` packages `em.store`** alongside `em` (the wheel was silently missing the subpackage).
- **EM-201: version is now single-sourced from `em.__version__`** (`3.0.0.dev0`, PEP 440 dev for the v3 line). `pyproject.toml` declares `dynamic = ["version"]` read via `[tool.setuptools.dynamic] attr = "em.__version__"` (this also fixes the previously broken flat-layout package discovery — wheels now build, packaging `em/`); the CLI `entropicmem.py` imports it instead of re-declaring a literal; `plugin.yaml` carries the same value, pinned by `tests/unit/test_em_version.py`. `skills/entropicmem/SKILL.md` intentionally stays at 2.8.0 (it describes the installed skill's behaviour, which is still 2.8.0 until 3.0 ships; bumped at EM-806/EM-904).
- **CI test matrix adds Python 3.13** and `pyproject.toml` gains the 3.13 classifier: Hermes Agent supports 3.13 and the full suite (927 passed, 2 skipped, 5 xfailed) already passes on it at 2.8.0. Python 3.14 is deliberately not added (Hermes cannot run on it).
- **CHANGELOG wording:** the EM-212/EM-213 known-limitation note no longer cites the old PR number (pre-cutover numbering doesn't exist in this repo); it now says "an earlier attempt was closed unmerged, pre-2.8.0 history".

### Fixed

- **EM-206: the v3 audit log is now hash-chained, verifiable, and readable from the CLI.** `em/store/audit.py` adds `append()` (called inside the caller's transaction, so a row and the change it describes commit together), `verify() -> VerifyResult(ok, first_bad_seq)` and the frozen digest `sha256(prev_hash || ts || action || actor || target_id || detail)`. The formula is duplicated from migration `0002` on purpose: that migration verifies the chain it rebuilt, so importing a shared helper would let a later edit silently invalidate a historical database. `detail` is stored canonically (`sort_keys`, no whitespace) so key order cannot change a digest, and any value longer than 128 chars is rejected, which is what keeps a fact body or transcript chunk out of the log.
  - New CLI: `entropicmem audit verify` prints `{"ok": true, "checked": N}` and exits non-zero with `first_bad_seq` on a break. The existing `entropicmem audit` listing is unchanged. The command reads the chain directly rather than through the v2 engine, because the v2 `audit_log` is unchained and would have reported OK on a tampered v3 store.
  - Verified against real data: a copy of the live 2.8.0 database migrates to 7168 chained rows and `verify()` confirms every one.
  - **Known limitation, now pinned by a test:** deleting a middle row *and* re-chaining the tail produces a chain that is internally consistent, so no adjacency check can detect it. Seq contiguity is not available as a defence either, because `0002` deliberately preserves the original v2 ids in `seq`. Closing this needs an anchor outside the database (publishing or signing the head digest); deliberately not built here.
- **EM-204: a fresh install was misdetected as a v2 database.** `0001` always leaves the *empty* v2 shape behind, so "a `facts` table exists" proves nothing about provenance. `0002` originally renamed those empty shells to `v2_*` and recorded `migrated_from='v2'` for a database that had never held a v2 row, leaving new installs littered with dead tables. The migration now decides from whether any source table holds a *single row*: a fresh install drops the empty v2 shells and produces a clean v3 schema with `migrated_from='none'`.
- **EM-204: `episodes`, `embeddings` and `audit_log` name collisions could have silently kept the v2 shape.** v2 and v3 both use those three names and the v3 DDL is `CREATE TABLE IF NOT EXISTS`, so if the v2 tables were renamed *after* the v3 DDL the `IF NOT EXISTS` would have been satisfied by the old v2 tables and v3 would never have been created — no error, just the wrong schema. Renaming now happens before any v3 DDL, and tests assert v3-specific columns (`window_seq`, `owner_type`, `prev_hash`) exist rather than merely that a table does.
- **EM-204: window episodes were classified as sessions.** Real ids are `ep_sess_{sid}_w{n}`, so testing the `ep_sess_` prefix first matched *every* window episode and labelled it a session — silently, since the column is just a string. The `_w\d+$` suffix is now tested before the prefix. Note the shipped v2 data contains no window episodes at all (0 of 1570 facts), so this rule is forward-looking and nothing in the real store would have caught it later.
- **EM-204: the FTS sync check was false assurance.** `INSERT INTO <fts>(<fts>) VALUES('integrity-check')` compares the index against the *content table*, so it passes even when the index is completely empty; `SELECT count(*)` on an external-content FTS table reads through to that same content table and therefore always agrees with it. Both reported a healthy index while holding zero documents. The parity check now reads the `<fts>_docsize` shadow table, which holds one row per actually-indexed document, and a test pins the false-assurance behaviour directly so the weaker probe cannot come back.
- **EM-206-prep: the privacy guard now covers the whole repo, and CI checks commit identity.** On 2026-09-26 an employer name reached `tests/fixtures/db/build_rich_v2.py` and `tests/unit/test_em_migration_v3_core.py` in published history, and five public merge commits carried a personal work email. Both are now guarded:
  - `tests/evals/test_no_personal_data.py` scans **every tracked text file** via `git ls-files` instead of a hand-picked glob list that omitted `tests/unit/` and `tests/fixtures/` (the exact blind spot the leak went through). Binaries are skipped, the guard excludes itself, and a new test asserts those directories stay covered so the list cannot silently shrink again. Two tokens were **removed** from the banned set because a repo-wide scan cannot ban them: they hashed to `fp` and `discovery`, ordinary words that appear in honest product code (`injection_screen.py`, `memory_engine.py`, `pyproject.toml`, `CHANGELOG.md`). Every real identifier stays covered, and a test pins both facts.
  - `scripts/check_commit_identity.sh` plus a new `identity-guard` CI job fail when any commit in range carries an author or committer email that is not `*@users.noreply.github.com`, `noreply@github.com` or `noreply@anthropic.com`. The **push-to-main** trigger is the alarm that matters: a GitHub web merge only creates its merge commit after CI has run on the PR, so the PR check cannot see it. The job checks both author *and* committer, since it is the committer field that GitHub sets from the merging account's email. Verified by mutation: a non-noreply author fails, a noreply author with a non-noreply committer fails (the real web-merge case), a clean range passes, and an empty range exits 0 instead of crashing.
- **EM-204: three EM-203 tests asserted a stale "migrated to latest == v2.7 shape" claim.** They were correct when `0001` *was* the latest migration and went false the moment `0002` landed. Rather than delete the coverage they were split by which migration's contract they actually pin: the v2.7-shape test now pins the registry to `0001` alone, a new parametrized test asserts the legacy ids and rows are still readable at *latest* (guarding `0002` against destroying what it must preserve for one release), and the empty-DB test asserts a clean v3 schema with no `v2_*` leftovers.
- **Graph server: malformed Host headers now return 400 instead of 500** (S1 follow-up). Starlette < 1.7 raised `ValueError("Invalid IPv6 URL")` while parsing a Host like `[::1` before the EM-114 allowlist ran, so the request died as a 500 (fail-closed, nothing served). The hardening middleware now reads the path from the raw ASGI scope and catches parse errors around the allowlist check only, so malformed hosts always get the same 400 `invalid Host header` response with security headers attached. Downstream handler errors are never masked: a corrupt `graph.json` still surfaces as an honest 500 (pinned by a regression test). Verified on starlette 1.0.0 (raises natively) and 1.7.0 (current pin).
- **Graph server: startup/shutdown hooks migrated from the deprecated `@app.on_event` to a `lifespan` handler** (S1 follow-up). Same behaviour: the non-loopback bind refusal, the per-run token file write and its shutdown cleanup are unchanged; the EM-114 security tests were updated to drive the lifespan and stay green.
- **`tests/test_phase11.py` tar extraction passes `filter="data"`** where supported (Python ≥ 3.12), matching the product import path and silencing the 3.13 deprecation warning. Test-only.

## [2.8.0] - 2026-09-25

Sprint 1 hotfix release (EM-101 to EM-118). Retrieval stops injecting noise and stops forgetting durable facts; writes stop silently overwriting; background work keeps its profile; Core Memory moves into the system prompt; export/import is consistent and fail-closed; the graph servers gain Host-allowlist, CSP and per-run-token hardening. Measured on the eval suites against the 2.7.0 baselines: ci recall@5 1.000 → 1.000, abstain_correct 0.000 → 1.000, noise_rate 0.286 → 0.143, must_not_ok 0.714 → 1.000; hard abstain_correct 0.000 → 1.000, noise_rate 0.303 → 0.214, recall@5 0.961 → 0.939. ### Fixed
- **Eval `--compare` gates only the §6.3 metrics (EM-117).** `compare_deltas` flagged every metric, so the `evals-ci` job failed on the S1 branch because `prefetch_tokens` rose 27.9 → 35.0, an intended EM-107 trade-off (provenance on injected bullets), while every gated metric improved. It would also have failed on any `latency_ms` jitter above 0.02 ms. Only `recall@5`, `ndcg@5`, `abstain_correct`, `noise_rate` and `must_not_ok` (`GATED_METRICS`, matching the CI workflow comment) now fail the gate; the other metrics stay in the table and are marked `info` when worse. Rows gain `gated`/`worsened`. Tested at the unit and CLI level (a non-gated worsening exits 0; a gated `noise_rate` regression exits 1).
- **`entropicmem graph serve` hardening (EM-114 follow-up).** The CLI served `--dir` through a bare `SimpleHTTPRequestHandler`: any bind was accepted (`--bind 0.0.0.0` published `graph.html`, which can embed note bodies, plus every other file and a directory listing to the network), there was no Host check, and the docs' "loopback bind enforced" claim was false. It now uses the new stdlib-only `graph_static.py`: a non-loopback bind exits `2` unless `ENTROPICMEM_GRAPH_EXPOSE=1` (and then prints an unauthenticated-exposure warning); the Host allowlist uses the same rules as the FastAPI server against the actually bound port (`--port 0` works); the same CSP/nosniff/no-referrer headers are sent; and only `/`, `/graph.html` and `/graph.json` are served. There is still no token, which is documented, with the FastAPI server as the authenticated option. `tests/test_graph_static.py` (22 cases, real sockets) covers Host accept/reject, path allowlisting (`/secret.md`, `/index.db`, traversal), headers on 200/404/400, HEAD/501, bind refusal in the module and the CLI, and a drift guard that fails if the CSP string or Host parsing diverges from `scripts/graph_server/server.py`.
- **Graph server request hardening (EM-114).** Additive patch to the canonical `scripts/graph_server/server.py` (no second `graph_server` package; the uncommitted plugin-side experiment was not adopted). (1) *Host allowlist:* an HTTP middleware refuses, with `400 invalid Host header`, any request whose `Host` does not name `127.0.0.1`/`localhost`/`[::1]` (or a loopback bind address) on the port taken from the listening socket (ASGI `scope["server"]`, so it follows the real `--port`; a portless Host means `:80`). With `ENTROPICMEM_GRAPH_EXPOSE=1` the concrete bind host and the new opt-in `ENTROPICMEM_GRAPH_ALLOWED_HOSTS` list are allowed too; wildcard addresses never are. It runs before the token gate and defeats DNS rebinding against the tokenless loopback trust plane. (2) *Security headers:* `Content-Security-Policy` (`default-src 'none'`; scripts only inline + `d3js.org` + `cdn.jsdelivr.net`; styles inline + Google Fonts; `img-src 'self' data:`; `connect-src 'self'`; `base-uri`/`form-action`/`frame-ancestors`/`object-src` `'none'`), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on every response, errors and Host rejections included. (3) *Random per-run token:* `secrets.token_urlsafe(32)` at process start is the credential whenever `ENTROPICMEM_GRAPH_TOKEN` is unset. It is written owner-only (`0600`, atomic) to `$HERMES_HOME/entropicmem/graph_server.token` at startup and removed at shutdown; with a static token configured the static token is the only accepted one and a stale file is deleted. `/refresh` therefore always needs a token (loopback included) but no longer needs a static secret to be usable. ## [2.7.0] - 2026-09-22

Hardening release. The engine moved into the plugin directory and every content-trust surface (writes, retrieval, prefetch, the graph viewer, the graph server) got explicit policy.

### Security

- **Write policy** blocks secret and credential content. High-confidence `api_key` / `password` findings are auto-redacted before storage; other PII types are recorded as warn-only findings.
- **Local prompt-injection screen** runs on vault retrieval and on prefetch, `recall`, and `get` tool payloads. Flagged content keeps its place and payload but ships prefixed with a prominent warning marker. Flag-with-warning and fail-open by design: if the screen itself fails, text ships unmarked rather than breaking retrieval.
- **Vault path containment** is enforced on vault writes, so writes cannot escape the resolved vault root.
- **Graph viewer markdown is sanitized** against stored XSS. Output from the markdown renderer and lazy-fetched note bodies both pass a client-side sanitize pass before touching the DOM.
- **Graph server loopback enforcement.** A non-loopback bind is refused at startup unless `ENTROPICMEM_GRAPH_EXPOSE=1` explicitly opts in. When not loopback-bound, the body-bearing read endpoints require `ENTROPICMEM_GRAPH_TOKEN` via the `X-EntropicMem-Token` header; loopback stays tokenless as the local trust plane.
- **Destructive operations gated.** `forget` and `consolidate` require `--confirm` and auto-backup before running; `consolidate` defaults to dry-run.
- **Append-only audit log** records every write.

### Changed

- **Engine relocation.** All engine code now lives under `plugins/entropicmem/scripts/` (previously `skills/entropicmem/scripts/`), making the plugin directory self-contained for catalog installs (`hermes plugins install entropicmem`). The skill `skills/entropicmem/` now holds only `SKILL.md`, `SETUP.md`, and `references/` plus vault templates. CLI invocations use `python3 ~/.hermes/plugins/entropicmem/scripts/entropicmem.py`.
- **Test suite and CI.** 600+ tests on Python 3.10 to 3.12 with pytest pinned in CI. The recall benchmark floor (`precision@5 >= 0.50`, `MRR >= 0.50`) is asserted in CI, and `hermes plugins validate --install-deps plugins/entropicmem` runs as the catalog admission gate.

### Added

- **Lifecycle hooks (5 total).** `on_memory_write` mirrors built-in `memory` tool writes into the engine (primary agent context only). `on_session_switch` tracks session identity and resets per-session caches. `on_session_end` writes an extractive session digest episode (deterministic id, re-firing replaces instead of duplicating) and runs quarantine-first fact extraction into `pending_facts`. `on_turn_start` flushes a partial digest every `turn_cadence_flush_turns` turns for always-on sessions, at most once per `turn_cadence_min_interval_sec`. `on_pre_compress` returns a standing-constraints bullet list to the compression summary prompt and durably checkpoints it as an episode (checkpoint API v2 fail-closed semantics: a non-empty return guarantees the checkpoint is persisted). All digest extraction is deterministic and stdlib-only (no LLM).
- **Lifecycle config keys** under `plugins.entropicmem`: `session_end_capture`, `turn_cadence_flush_turns`, `turn_cadence_min_interval_sec`, `session_extract_pending`.
- **Explainable recall.** Every `recall()`, `recall_with_relevance()`, and `recall_hybrid()` hit carries a `why_retrieved` field: a deterministic list of reason tokens (`exact`, `fts`, `vector`, `recency`, `importance`, `triple`, `domain`) explaining why the fact surfaced. The `entropicmem_recall` tool exposes it in tool output.
- **Recall benchmark.** Frozen corpus (98 facts) with 20 probes, a single runner (`benchmarks/run_recall_bench.py`) reporting `precision@5` and MRR, and a CI floor of 0.50 on both.

### Fixed

- **Graph exports render again.** Exports showed an endless "Building graph" spinner because a node color helper referenced by the export template had been deleted; every export threw a `ReferenceError` before the simulation started. A template integrity test now scans for helpers called without a definition.
- **`lint` dead-link detection is order-independent.** Wikilink targets are collected before validation, so a link to a note that sorts after the linking note is no longer reported dead.
- **Graph export crash under `--max-nodes` re-ranking.** Edge dataclass objects were dereferenced as dicts (`TypeError`), failing exports and CI; fixed to dataclass attribute access.
