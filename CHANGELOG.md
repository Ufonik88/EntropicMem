## [Unreleased]

### Added

- **EM-401, slice 1 — the §4.1 hook skeleton, the pinned host contract, and a harness that drives every hook.**
  - **`em/provider/hooks.py` — `fail_soft`.** Every hook the host calls is wrapped: timed, counted (`hook.<name>` metrics), over-budget logged at WARNING, and exceptions swallowed — logging the exception **type only**, because a tool handler's message can carry the user's text (the detail stays at DEBUG). **Fail-closed, and deliberately stronger than the card's carve-out:** `on_pre_compress`, `initialize`, `save_config` and `backup_paths` re-raise, because §4.6 counts *any* non-raising return as a successful checkpoint — swallowing a failed one claims a persist that never happened. The hook that *should* fail soft (a skipped or absent checkpoint) does so inside its own body, returning `""`. Recorded as a deviation from the card's blanket "swallows exceptions".
  - **`em/provider/state.py` — `ProviderState`.** Session id, agent context, last recall count and the core baseline in one holder; the provider's `_session_id` / `_agent_context` / `_core_baseline` are now properties over it, so no call site changed and no second copy can drift. `writes_allowed()` keeps the primary-context rule in one place.
  - **`em/provider/provider.py` — the §4.1 surface table.** One row per hook with its thread, its budget and its status. `on_delegation` (EM-405) and `identity_signature` (EM-402) are the two **deferred** rows, each naming its card and why. `recall_status` and `unavailable_reason` are newly implemented, and the injected count now rides with the cached prefetch block so a cache hit can still report what it injected.
  - **The contract test (EM-401's AC).** `tests/test_provider_contract.py` enumerates `MemoryProvider` from the pinned hermes-agent — pinned as a dated copy at `tests/harness/pinned_memory_provider.json`, so CI needs no host, and **re-derived and compared against the real host whenever it is reachable** — then asserts every method is implemented or explicitly deferred, that the provider's signatures still bind the host's calls, that `pre_compress_checkpoint_api_version = 2`, and that `plugin.yaml`'s `provides_hooks` is exactly the hook set the provider has (the catalog review verifies those lists).
  - **The harness (EM-401's other AC).** `tests/harness/test_provider_hook_surface.py` drives every §4.1 hook — the turn path through FakeHost with an author, the boundary and tool hooks directly — and reads the `fail_soft` metrics to prove each one ran **and none recorded an error**. `on_turn_start` now names the §4.1 author trio, which is what makes the host pass it.
  - **`_backend.bootstrap_scripts_path()`** puts the plugin's own scripts dir on `sys.path` at import time (the same candidates `resolve_scripts_dir` uses), so `em.provider.*` can be imported before `initialize()` has resolved a home.
  - Evidence: 37 new tests; **2221 / 5 / 3** bare and **2223 / 3 / 3** with numpy on Python 3.10 and 3.12; `ruff==0.16.2` clean; the privacy guard clean **in place**. **13 mutation checks, all red** — the swallow, the fail-closed carve-out, the over-budget warning, success metrics, `recall_status` reporting, `writes_allowed`, the cache-hit count, a dropped host signature, a dropped surface row, a vacuous audit, a lost manifest row and a renamed deferred hook.
  - **Not in this chunk, deliberately:** the provider class has **not** moved out of `plugins/entropicmem/__init__.py` into `em/provider/provider.py`. A ~1700-line move bundled with new hook semantics would be an unreviewable diff; the skeleton lands first and the move is EM-401's next slice, with EM-402 (ScopeContext) and EM-403 (PrefetchService) after it.

- **EM-303 observability, promotion evidence, and model-switch hygiene (the owner's precision list).**
  - **Per-query vector observability, so a silent recall drop is visible.** Every vector-mode generator call logs `coverage` and `stale_excluded` on the `em.retrieval.vectors` logger — an INFO line per query, and a WARNING whenever vectors were excluded as stale. A **stale→re-embed round trip is pinned for memories and episodes**: the edit excludes and logs, and the normal `embed` queue returns the row to results without manual repair.
  - **The vector tests cannot be silently skipped.** `tests/test_vector_ci_guard.py` fails if CI's test job loses numpy, stops running the full suite, or either numpy-gated test disappears. Documented: on a bare box the 5 skips are the two numpy tests plus the two internal-ops scripts and the private digest list; with numpy both pass. CI installs numpy (merged in the follow-ups) and runs with the digest list, so the cache/AC tests run on every merge.
  - **Vector-mode evals exist and are labelled.** A new explicit `evals run --embeddings/--no-embeddings` override leaves the frozen suites lexical by default while making a deliberate vector run possible. With `fastembed`/`BAAI/bge-small-en-v1.5`, the hard suite reads **recall@5 0.988, ageing 1.000, paraphrase 1.000, noise 0.172, abstain 1.000** against lexical 0.933 / 0.733 / 1.000 / 0.172; the ci suite is at parity. Committed baselines: `evals/baselines/v3-hard-vector.json`, `v3-ci-vector.json`; both comparisons printed cross-mode and never gated. **Live retrieval remains lexical until EM-401–403.**
  - **Promotion gate recommended and recorded** (owner confirms before the live flip): coverage ≥ 95% with `stale_excluded == 0` on the qualification sample; hard recall@5 ≥ 0.95; ageing ≥ 0.85; abstain ≥ 0.95; noise ≤ 0.172; must_not_ok = 1.0; turn-path p95 ≤ 150 ms at 50k; the shadow's `v3_only == 0` still holding.
  - **Model-switch hygiene.** Measured **≈2.1 KB/row all-in (1.5 KB blob): ≈21 MB per 10k memories per model set** (50k → 106 MB per stale set). Policy decided: prune non-current-model rows after a completed backfill for the current model plus a **7-day grace**, keeping the current and previous models, executed by EM-410's maintenance pass. Tests prove a partial new-model backfill never uses old-model vectors — memories **and** episodes.
  - **Idempotence oracle strengthened:** the replay test now judges by row count plus a sha256 over every column of `embeddings`, not `created_at` alone.
  - **EM-411 stays unbuilt and default-off**; its first implementation commit is specified as the two test groups most likely to waste jobs or double-extract (a shared window key across cadence/idle/compaction seals; the idle `min_window_turns`/`min_window_chars` floor).
  - Evidence: 6 new tests; **2184 / 5 / 3** bare and **2186 / 3 / 3** with numpy on Python 3.10 and 3.12; `ruff==0.16.2` clean. Six mutations red: observability removed, the episode stale count zeroed, CI's numpy removed, a gated test renamed away, and the model filter neutralised for memories and episodes.

- **EM-303 precision pass: version-checked vector rows, the episode read path, and retrieval-mode labels on every eval report.**
  - **Every vector row now records and is checked for model, dimension and text version.** The model id is already the primary key (`embeddings(owner_type, owner_id, model)`), so a model switch can never mix rows — reads filter by the configured model and the backfill adds the new model's rows beside the old. Reads also filter to the query's **width**, so a same-name artifact whose dimension changed is neither padded nor a crash. And the **text version is verified on every read**: a memory vector only serves when its stored `content_hash` matches the memory's current one; an episode vector when its stored stamp matches `updated_at` (an empty stored hash means "unverified", kept for pre-EM-303 rows). A stale vector is excluded — coverage drops and the queued re-embed restores it — never silently mixed. `embed_backfill` now writes real hashes/stamps instead of empty strings.
  - **Episode vectors are no longer write-only.** `candidates.episodic` appends vector-ranked episodes under the same 50% coverage gate as memories, and the pipeline hands their cosines to the gate's support test, so EM-307's renderer prints a vector-only paraphrase under "Recent episodes". Lexical and vector hits of the same episode collapse to one row.
  - **Backfill idempotence and resume are pinned.** A replayed backfill changes nothing (rows, `created_at`, vectors all byte-identical — the no-rewrite tell), and a mid-run backend failure leaves the first 64-row page intact with the second run completing to exactly the expected rows, no duplicates.
  - **Every result file and comparison carries `retrieval_mode`** (`lexical`/`vector`), and `evals run --compare` prints both modes: a cross-mode comparison (including against a pre-label file) is context only and never gates. All six committed baselines are labelled `lexical` — verified by construction, since `ci`/`hard` force embeddings off. `evals tune` records its mode too.
  - The status doc now says plainly that **live retrieval is lexical until EM-401–403**; no semantic-retrieval claims without that wiring. The capture feature's design points (shared window dedupe key across all triggers, post-commit enqueue that cannot fail the checkpoint, idle minimum-content floor, and the 4–9 extraction-jobs-per-100-turn estimate) are written into **EM-411**'s spec, still unbuilt.
  - Evidence: 12 new tests; **2178 / 5 / 3** bare and **2180 / 3 / 3** with numpy on 3.10 and 3.12; `ruff==0.16.2` clean. Seven mutations red, each against the guarantee it targets: the memory hash check, the episode stamp check, the width filter, episode vector recall, episode gate cosines, the v3 mode label, and cross-mode detection.

- **EM-303's follow-ups: episodes become embedding owners, evals can embed, and numpy runs in CI.**
  - **Episodes are embedded too.** `EpisodeStore.add_episode`/`upsert_episode` enqueue an `embed` job shaped `{owner_type: "episode", owner_id, stamp}` (`updated_at` is the version, since episodes have no `version` column); the handler embeds `title + summary` and re-checks the stamp **inside the write transaction**, so the same race guard the memory path has applies. `embed_backfill` now pages memories **and** episodes (`pending_embed_texts`), and `meta.embedding_model` still records only on completion. The memory vector generator deliberately ignores episode rows (they render through EM-307's episode sections).
  - **The v3 eval adapter can produce query embeddings.** With `disable_embeddings=False` (what `evals run` passes for any suite that is not `ci`/`hard`), the adapter embeds the scenario's documents at `load()` and the query in `_run()`, passing both into `pipeline.retrieve` — the vector generator and the gate's cosine condition become measurable end-to-end. The frozen suites pass `True` and stay byte-identical lexically; a `none` backend changes nothing anywhere.
  - **CI installs numpy**, so the vector-cache agreement tests and the card's 50k p95 < 25 ms AC actually run in the ordinary test job instead of skipping (the same fix fastapi got earlier).
  - Evidence: 9 new tests; **2166 / 5 / 3** on 3.10 and 3.12 on a bare box, **2168 / 3 / 3** with numpy installed (`ruff==0.16.2` clean). Five mutations went red: the episode enqueue removed, both episode stamp guards removed, the backfill's episode branch removed, document embedding removed, and query embedding removed. Two first-draft test gaps were found and fixed on the way — the episode stale test needed a real race (a replay is harmless because the handler re-reads), and the first mutation attempts hit the wrong call sites, which is itself the check working.

- **EM-303's closing slice — backends, jobs, model identity, and the numpy vector cache.**
  - **Backends** (`em/embeddings/backends.py`): `fastembed` (ONNX, no torch; default `BAAI/bge-small-en-v1.5`, 384-d, preferred), `sentence_transformers` (default `all-MiniLM-L6-v2`), `openai_compat` (stdlib `urllib`, env `ENTROPICMEM_EMBEDDINGS_BASE_URL`/`_API_KEY`/`_MODEL`), and `none`. `auto` picks the first available in that order; an explicit name that is unavailable **falls back to `none`**, never raises. The optional stacks are imported lazily, so `em` stays stdlib-only.
  - **Service** (`em/embeddings/service.py`): batches of ≤ 64, `summary or content` (≤ 2,000 chars) for memories, `title + summary` for episodes, idempotent `warm()`. No prefetch path may call it.
  - **Jobs** (`em/embeddings/jobs.py`): `embed` re-checks the row's `version` **inside the write transaction** — a lease-expired duplicate that read v1 and embedded while v2 landed cannot clobber the newer vector. `embed_backfill` pages 64 at a time, heartbeats between batches, and writes `meta.embedding_model` only on completion; `ensure_embedding_model` queues one backfill per new model (dedupe key). Without a backend both are a clean no-op — no dead jobs on a box without fastembed, and the backfill catches up once one is installed. The worker CLI registers both types.
  - **Vector cache** (`em/embeddings/cache.py`): one snapshot per `(db, model, scope, mode)`, invalidated by `(row count, max rowid, write generation)` — `put_embedding` bumps the generation. Numpy gives one matrix-vector product per query; without numpy the same ranking comes from the pure-Python cosine. Scope filtering stays in `scope_sql` (the doc records why not "id→scope masks": a second copy of the §3.5 rule would drift). Migration **0005** indexes `embeddings(owner_type, model)`. `candidates.vector` and MMR now read through the cache.
  - **Measured:** 50k × 128 vectors, warm search **p95 3.86 ms** (p50 3.68, max 3.88) against the card's 25 ms AC; cold cache build 297 ms. The AC test needs numpy — now installed by CI (see the follow-up entry above), so it runs there; the pure-Python agreement path is tested everywhere.
  - **Recorded caveat:** a raw-SQL rewrite of a vector that leaves count, max rowid and the generation unchanged is not re-read until the cache resets — the same shape v2's cache had; every write through the store helper is seen. Pinned by a test.
  - **Extras follow the card:** `semantic` is now `fastembed>=0.3`; the v2 re-ranker stack moved to `semantic-st`.
  - **A latent test flaw the change exposed:** the backup tamper test wrote `\x00` over the last byte, which after migration 0005 is already zero — a no-op "tamper". It now flips the byte; the refusal is still asserted.
  - Evidence: 34 new tests; **2157 passed / 5 skipped / 3 xfailed** on Python 3.10 and 3.12 (`ruff==0.16.2` clean). Mutations proven red: the selection order swapped, the batch cap doubled, the model record dropped, the write-time version check removed, the snapshot's tie-break sort removed, and the cache fingerprint ignored. Two first drafts survived and each exposed a real gap — the stale-job test had no race and the tie sort had no observable SQL order — both fixed (the handler gained the write-time recheck) and re-run red.

- **EM-303 — MMR's embedding path.** `diversity.mmr` takes an optional `similarities` callable, called as `similarities(candidate, chosen)` and returning a redundancy in `[0, 1]`; `pipeline.retrieve` supplies one when the caller gave a query vector and a model — **cosine when both candidates have a stored vector (clamped at 0, because an opposed pair must not earn a bonus), token Jaccard per pair otherwise**. With `similarities=None` the behaviour is exactly what every previous caller had. Nothing embeds; no backends, cache or job yet.
  - Evidence: 4 new tests; **2125 passed / 3 skipped / 3 xfailed** on Python 3.10 and 3.12; `ruff==0.16.2` clean. Three mutations went red: the pipeline's similarity suppressed, the negative-cosine clamp removed, and `mmr` ignoring a supplied callable.

- **EM-303, first slice — the vector generator searches embeddings *already stored*.** `em/store/embeddings.py` decodes the blobs v2 already writes (native float32, one query per search) and computes cosine in stdlib; `candidates.vector` joins `embeddings` to active, in-scope memories and runs only when the caller supplies **both** a query vector and a model, **and** §3.6's coverage gate holds (≥ 50% of active memories in scope carry a usable vector for that model). `retrieve(..., query_vector=…, embedding_model=…)` is the seam: it passes both to the context and turns the gate's cosine condition on for that call, but only when no explicit `gate_config` was given. **The default call passes neither**, so the generator returns `[]` and issues no SQL — the lexical path is unchanged and the eval adapter is untouched.
  - **What this slice deliberately does not include, recorded:** the embedding backends (`fastembed` / `sentence_transformers` / `openai_compat` / `none`), the `embed` job, the model-switch backfill, and the numpy matrix cache. Nothing on this path embeds — asserted by a test that the generator issues no SQL without a query vector. An unknown model gets no invented threshold: §3.6 names two, and a hit for any other model cannot pass on cosine.
  - Evidence: 11 new tests; **2121 passed / 3 skipped / 3 xfailed** on Python 3.10 and 3.12; `ruff==0.16.2` clean. Three mutations went red: the coverage floor removed, cosine left unnormalised, and the pipeline failing to enable cosine when a query vector is supplied.

- **EM-307 — the token packer and §3.6 renderer.** `em/retrieval/packer.py` greedily spends `prefetch.token_budget` (default 450) by score: a row is rendered in full when the block still fits, otherwise as its summary, otherwise skipped — never cut mid-sentence. `em/provider/render.py` emits §3.6's block (Constraints, About the user, Relevant memories, Recent episodes, Open follow-ups), cites `em.clock.short_id` as `[m·…]` / `[e·…]`, and places a superseded note as `(kind · updated <date>; was: <old>)`. Untrusted text has `<memory-context` / `</memory-context` broken with a zero-width space and a leading `#` escaped as `\#`. Injection-flagged rows keep v2.7's warning marker; `on_flagged="drop"` is the EM-703 hook and is not the default.
  - **Landed unwired.** The library commit did not call it from `pipeline.retrieve`, the eval adapter, or the provider. The entry below wires a retrieval through to the renderer; the adapter and the provider still do not. `em/config.py` is not read.
  - **The card's ±15% tiktoken check does not hold, and the estimate was not changed to make it.** §3.6 names `ceil(len/4)`. On a 222-character prose sample, cl100k (also o200k, p50k, r50k) counted 42 tokens against this function's 56 — about 33% high. The error is conservative (we pack less, not more). Importing tiktoken when present would pack differently per machine, and `em` is stdlib-only. A repeated-stopword sample can be forced inside 15%; that would be fitting the check.
  - Evidence: 13 new tests; **2103 passed / 3 skipped / 3 xfailed** on Python 3.10 and 3.12; `ruff==0.16.2` clean. Mutation checks that removed the summary fallback, the tag break, the heading escape, the score order, and the section order each went red.

- **EM-307 — a gated retrieval can be rendered.** `pipeline.retrieve(..., with_gate=True)` now returns the predecessors the collapse already computed, and only for keys MMR kept. `load_pack_items` reads content and summary as separate columns, quotes the newest predecessor as `was`, and turns an episode's open loops into follow-up rows at a slightly lower score. `render_retrieval` packs that into §3.6's block. `cite="full"` puts the stored id in the brackets; the default stays the short citation.
  - **The eval adapter still does not call it.** Its prefetch is still `- [stored id] text` with no budget. A short citation would stop `parse_injected_ids` matching, and the 450-token budget can drop an id the old bullet emitted. That switch stays a separate change, and it should be measured on the hard suite before anyone makes it. `em/config.py` is still not read. The flag stays off.
  - Evidence: 7 new tests; **2110 passed / 3 skipped / 3 xfailed** on Python 3.10 and 3.12; `ruff==0.16.2` clean. Three mutations went red: the predecessor map dropped, `was` cleared, and `cite="full"` turned into a no-op.

- **EM-306 — the calibration harness: `python -m evals tune` splits the hard suite by id hash, searches a pre-declared grid, and commits what it chose.** The split is `sha256(scenario_id)[:8] % 100 < 70` → dev, so a rerun on a later commit scores the same holdout — the rule and its concrete ids are recorded in the result file. The objective is the card's, on the **dev** split only: `0.4*recall@5 + 0.3*mrr + 0.3*abstain_correct − 0.2*noise_rate`. The grid is declared in code before any run (`gate.min_score ∈ {0.25, 0.30, 0.35}`, `gate.min_coverage ∈ {0.30, 0.34, 0.40}`, three rerank-weight presets), and selection is "highest dev objective; ties prefer the candidate closest to the spec" — the first pass found a flat tie in the `min_score` band, so a flat objective must not move a threshold by accident.
  - **One seam in the real pipeline, not a second pipeline.** `pipeline.retrieve` takes optional `gate_config`/`rank_weights` (defaults: the spec) and the v3 adapter threads them, so every tuned number is a number for the code the provider will call. Tests show an override reaches the stage it names, and that `None` is the spec.
  - **What the run found, holdout included.** 27 candidates on 44 dev scenarios (126 turns); the holdout (16 scenarios, 28 scored turns) was never optimised. Chosen: the gate thresholds **unchanged at the spec's 0.30/0.34** (the dev objective was flat across the band) and the rerank weights moved to `importance_heavy` (rrf 0.50 / importance 0.25 / recency 0.10 / confidence 0.10 / feedback 0.05) — dev mrr 0.917 → 0.919, holdout mrr **0.865 → 0.881** with the same recall (0.869) and noise (0.115). Committed as `em/config.py` scalars and `evals/results/tune-hard-4eb8097.json`; `em/config.py` links the file back and a test pins the two together.
  - **Deliberately not tuned, recorded in the result file's `deferred` block:** the per-intent `GENERATOR_WEIGHTS` tables (a 4×6 space the card does not name) and the per-model cosine thresholds (grid empty until EM-303).
  - **CI's eval gate stays v2, decided here and written on the job:** the tuned defaults are not wired into call sites until EM-401–403, so a v3 gate today would enforce the spec defaults, not the calibration; `tests/evals/test_adapter_v3.py` remains v3's regression protection in the ordinary suite.
  - Evidence: 18 new tests (14 in `tests/evals/test_tune.py`, 3 in `tests/unit/test_em_retrieval_pipeline.py`, 1 in `tests/evals/test_adapter_v3.py`); **2090 passed / 3 skipped / 3 xfailed** on both Python 3.10 and 3.12; `ruff==0.16.2` clean; **12 mutation checks, all as expected** — each override dropped, the split re-hashed, the objective re-weighted, the tie-break removed, and the armed value, config, result and rule each drifted, all caught.

- **A cited-SHA guard: every SHA written into a doc or a landing commit must resolve.** `tests/test_cited_shas.py` scans every 7–40 character hex token in tracked markdown and in the messages of commits not yet on the base branch (`main`, falling back to `origin/main`), and fails on any token that does not resolve to a commit unless it is in an explicit allowlist with a reason. The allowlist is the closed set of tokens cited on purpose that cannot resolve — the seven dead SHAs from the scrubbed history, the upstream fork commit, and the date in the `rollback/pre-s1-20260924` tag name — and an honesty test fails if an entry stops being cited or starts resolving, so it cannot rot into a place to park a real SHA.
  - **Why it exists:** a docs commit cited a SHA that did not exist (recorded at `7c2fdf9`), and the document-control guard caught it only by luck of position — the token sat in the `Last reconciled` line, the one place that guard checks. The same token in any other doc, or in a commit message, would have landed, and a citation that does not resolve makes the record unfalsifiable. Published history is deliberately out of scope: it is never rewritten (rule 9) and legitimately cites dead and upstream SHAs, so the check is the docs tree plus the commits about to land.
  - **Not a vacuous scan:** sanity floors (≥ 20 markdown files, ≥ 50 tokens) fail if the regex or the glob breaks, and a pin shows a blob hash is not a commit citation. Evidence: 6 new tests; **2072 passed / 3 skipped / 3 xfailed** on both Python 3.10 and 3.12; `ruff==0.16.2` clean. **11 mutation checks, all behaving as expected** — including a blindness proof (disabling the resolution check lets a fabricated token through, which is why that check is the guard) and one defect ruff found: an undefined name in the failure path would have made the commits half crash instead of assert, the exact "cannot fail for the right reason" shape.

- **A guard for the pre-flight count itself: the three pages that state the expected suite size must now agree.** `tests/test_master_todo.py` extracts the `passed / skipped / xfailed` triple from `MASTER_TODO`'s gates table, `NEXT_CHUNK.md`'s pre-flight and `REMAINING_PLAN.md` §11's verify block — one anchored line each — and fails if they disagree, if an anchor stops matching exactly one line, or if a page drops out of the comparison. **Cross-file agreement only, deliberately:** comparing against a live collection would need a nested pytest run, which trades a silent drift for a flaky gate (and `--collect-only` cannot see collection-time skips, so the number would not match regardless). The drift it exists for is real, not hypothetical: Chunk 18's pre-flight said **1995** while `MASTER_TODO` and the actual run said **1998**, and the rule on mismatch is "stop and report" — so one stale page costs a full re-measure and invites exactly the wrong conclusion ("assume the older number is right").
  - **The comparison is a pure function (`_baseline_disagreement`) fed synthetic violating inputs**, because the docs agree today and a guard whose only input is an agreeing tree cannot be mutation-proven: weakening its `len(...) > 1` test slipped through green until disagreement was handed to it directly. Nine mutation checks — **eight caught**; the one survivor is a knowingly redundant assertion (the in-doc drift probe), which the synthetic tests already cover, and it is labelled belt-and-braces in the code rather than left looking load-bearing.
  - Evidence: 5 new tests; **2066 passed / 3 skipped / 3 xfailed** on both Python 3.10 and 3.12; `ruff==0.16.2` clean. No product code touched.

- **P0c — the shadow readout: a divergence log can now be *scored* against the frozen observable, and collected honestly.** The promotion observable (`≥ 200 turns, copy within 900 s, divergence ≤ 10%, v3_only never non-zero, off-turn p95 ≤ 150 ms`) has been fixed in `_shadow.PROMOTION` since Chunk 17, but nothing could read a log against it, and the live store holds **zero facts** — so the only sample a dev box could produce was one that measures nothing. Two pieces landed; **no threshold was moved**:
  - **`_shadow.evaluate / read_log / report / render / main`** score a log in place, next to the thresholds it uses, so the two cannot drift. Thresholds are read from `PROMOTION` *at report time* (tightening the dict changes the verdict — a copied literal cannot). The verdict is `met` / `not met` / `cannot conclude`, and the rules that make a green light mean something are all asserted: **a short, unreadable or no-signal sample is never `met`** (an empty store makes v2 and v3 both inject nothing, and a naive rate reads that as 0% divergence — a fake pass handed straight to the owner); **a violation outranks a short sample** (one fabricated hit in three turns is `not met`, so "we need more data" can never dissolve a finding); and the writer's own fields are **cross-checked**, not trusted — `stale` against the bound in both directions, `divergence`/`v3_only` against the ids on the line, with disagreement refusing to read as fresh.
  - **Margin, distribution and findings, not just a pass/fail**, because that is what the owner asked to see: every number carries how much room was left before it would have failed (rates in points, not bare fractions — the seeded run showed the difference), `p50/p95/max` together (the `perf-smoke` tell: a low p50 with a huge max is one noisy sample), the alternate denominators as context *while the verdict uses the frozen one*, and the first offending line numbers and ids. **Findings cite line numbers and ids and never question text** — the log holds the user's question, and a report is something you paste into a ticket or to an agent.
  - **The runner is `python plugins/entropicmem/_shadow.py report [--log PATH] [--json]`, deliberately not an `entropicmem shadow report` CLI command.** `plugins/entropicmem/__init__.py` imports `agent.memory_provider`, so the v2 CLI cannot import the provider package in a plain shell; going through it would have failed closed with an `ImportError` and no clearer error than this note. The structural reason is pinned: a test parses `_shadow.py` and fails if it ever gains a module-level relative or host import, because that breaks the collector silently and nothing else would. Exit code is the verdict: 0 met, 1 not met, 2 cannot conclude.
  - **`scripts/shadow_collect.py` collects a sample.** It copies the store it reads with `sqlite3.Connection.backup` from a `mode=ro` connection, runs the **real v2 engine** on the copy for `v2_ids`, and drives the real `_shadow.run` per turn — so the migration path, the S3 pipeline and the latency are all genuine. **It never writes the source** (asserted on bytes *and* mtime, not by reading for a `mode=ro`), it restores the two env vars it borrows, and it refuses a `--source` that is not there rather than degrading to an empty store. - **EM-305 — the abstention gate, supersession collapse and MMR diversity (§3.6).** `em/retrieval/gate.py` and `em/retrieval/diversity.py` complete the v3 retrieval pipeline's decision stages: the gate decides whether a memory block is shown at all, the collapse removes duplicates and superseded duplicates, and MMR keeps the surviving block diverse.   - **The "post-stem" coverage trap is resolved exactly, not approximated.** §3.6 defines coverage as "matched non-stopword query terms (**post-stem**) / total query terms, computed in Python on the candidate text", and §3.2 forbids non-stdlib dependencies (no Python porter stemmer). - **EM-210 (Chunk 3.2): the once-per-hour-per-reason snapshot throttle.** `BackupManager.snapshot_if_due(reason, *, window=3600)` writes a snapshot only when that reason has had none inside the window and returns `None` while one is still young, so a destructive caller that fires in a loop cannot fill the backup directory: 100 `forget` calls inside an hour write exactly one snapshot, which is the plan's acceptance criterion. ### Security

- **Chunk 13 — §3.5's `visibility` half, both sides: the write stamp and the read guard.** *Provenance: proposed by the implementing agent and implemented under the owner's authorisation; **ratified by the owner on 2026-10-07 as a ruling** on the behaviour change — `row_is_owner_only()` as the single owner-only predicate, the restored `_outbox` sensitivity gate, and `_resolved_visibility()` stamped at insert. **Internal only:** it is in no release and must not reach the marketplace until the owner explicitly approves a release. No migration, so it is reversible with a code revert alone.*
  - **The bug, measured.** `MemoryDraft.visibility` defaulted to `'user'` and **no call site anywhere set it**, so every `MemoryStore.add` — the facade's `remember` included — stamped `'user'` whether the row was profile-wide or user-scoped. §3.5 pairs `'user'` with a *user-scoped* write and `'profile'` with a profile-wide one, and makes a profile-wide row carrying `'user'` **owner-only**. The store was therefore producing, for every write, exactly the row shape its own plan calls private.
  - **The direction of the fix is the whole point, and it is why the read clause could not ship alone.** Implementing the read clause on its own would have hidden *every* profile-wide memory from non-owners — the opposite of §3.5's intent that profile-wide `public`/`internal` rows are shared knowledge. The write stamp is the real fix; the read guard is the defence for rows that already exist or that a caller deliberately stamps. `test_a_non_owner_still_sees_an_ordinary_profile_wide_row` is the regression guard, and the cross-check matrix in `tests/unit/test_em_retrieval_scope_sql.py` gained the row shape so the SQL and the predicate are compared on it.
  - **What changed.** `MemoryDraft.visibility`'s default is now `''`, meaning *derive from the scope* — a plain `str` default cannot tell "the caller asked for `user`" from "nobody said anything", and the difference is load-bearing. `MemoryStore._insert` resolves it (`'profile'` for a profile-wide write, `'user'` otherwise, a caller's explicit value preserved and never overridden). On the read side `em.store.types.row_is_owner_only` now owns *both* owner-only conditions — the tier, and a profile-wide row stamped `'user'` — and `_in_scope` and `em.retrieval.candidates.scope_sql` both call it, so the predicate and the SQL cannot drift.
  - **A publication consequence, fixed rather than inherited.** `_outbox` queues a row for sync when `visibility in ('profile','shared')`, and its docstring said "anything sensitive stays local" — but the code only ever checked `visibility`. That was sufficient *by accident*, because the old `'user'` default meant a profile-wide write was never queued at all. v2's gate was `_publish_allowed(sensitivity)`, so **v2 published every non-sensitive fact and this restores that**, with the tier check now explicit. Without it a profile-wide `sensitive` row would have started reaching the sync outbox — a leak this chunk would otherwise have introduced.
  - **`MemoryStore.list` was investigated and left alone, with the reason now recorded.** Its `scope_user=?` is *exact*, so a scoped caller can only receive rows already scoped to them — every one of which they may read, whatever its tier — and the profile-wide rules govern rows it cannot return. The Chunk 7.2 note that it "is not tier-filtered" is therefore not a leak; `test_list_never_returns_a_profile_wide_row_to_a_scoped_caller` pins it.
  - **The fix is forward-only, and no existing data needs repairing — stated because silence would be read as "history is clean".** Nothing in the released world was ever affected: the v2→v3 migration stamps **`visibility='profile'`** for every migrated fact (so migrated rows are profile-readable, *not* the owner-only shape), the only producer of the owner-only shape was `MemoryStore.add`'s old default, and the live store is `user_version=0` with v2 tables only. **There is therefore no repair path, no backfill, and nothing hidden from a non-owner today.** A v3 store written *before* Chunk 13 and read *after* it would keep its historical stamps, by design — those rows are owner-only, which fails closed — and since no such store exists outside test fixtures, that is a statement about the contract rather than about data.
  - **Reversible, and it adds no migration.** `LATEST` is unchanged, asserted by `test_the_change_adds_no_migration`. Existing rows are never rewritten: only new writes derive a stamp, and the read guard changes only what a non-owner sees. Rows written while this is live keep their stamp, so a revert restores future behaviour rather than rewriting history — and with v3 stores unreleased and the live store v2 with zero facts, there is nothing to unwind.
  - **The contract for rows that already exist is derive-on-write-only, deliberately.** Only *new* writes derive a stamp; historical rows are never rewritten, and the read guard changes only what a non-owner sees. The consequence is stated rather than hidden: a pre-existing profile-wide row carrying the old `'user'` default is **owner-only** under §3.5's literal rule — it fails closed. Re-deriving those rows would be a bulk change to who may read what, so it is a one-off owner-approved migration if it is ever wanted, never a silent rewrite. In practice there are none: v3 stores were never released and the live store is v2 with zero facts, so this exists only in test fixtures. `test_reads_do_not_rewrite_the_stamp` and `test_the_change_adds_no_migration` pin it.
  - **Nothing consumed the rows this gate stops, and nothing had been queued by the old path.** The only consumer of `sync_outbox` is v2's `MemoryEngine.publish()`, which drains `emitted=0` into the shared `sync_events` log; on a v3 store that path is *unreachable*, because `entropicmem publish`/`pull` are refused by name until S5, and **no `em/` code reads the outbox at all** (it writes, and `forget` deletes). Nothing queued a profile-wide sensitive row before Chunk 13 either: v2's `_publish_allowed` refuses `secret`/`sensitive` outright, and v3's old default stamped `'user'` so `_outbox` returned early — no call site ever combined an explicit `'profile'` visibility with a sensitive tier. So there is nothing to replay, drop or backfill; already-queued rows are all non-sensitive and stay queued, and the v2→v3 migration leaves the table untouched (legacy `fact_id`s preserved until EM-309).

- **EM-209: durable job queue and worker.** `em/store/jobs.py` adds `JobQueue` over the v3 `jobs` table; `em/jobs/` adds `JobWorker`, `HandlerRegistry`, `JobContext` and `PermanentJobError`. This is the path for everything slow or retryable (embeddings in EM-303, summaries, maintenance), so nothing slow ever runs inside a write transaction.
  - **Handlers run outside every transaction.** The worker uses one short write transaction to claim, one per heartbeat, and one to complete or fail. The handler runs between them, so an embedding or LLM call never holds the SQLite write lock. A test asserts the writer is not in a transaction while the handler runs.
  - **Claims are atomic across processes.** The claim runs under `BEGIN IMMEDIATE`. The acceptance test runs 4 worker processes against 300 jobs behind a start barrier: every job runs exactly once, and the work is shared. Claiming outside the transaction was mutation-checked and produces double runs.
  - **Leases, and a crash counts as an attempt.** A claim sets `locked_by`/`locked_until` and increments `attempts` up front, so a job whose handler kills the worker still reaches `max_attempts` and goes `dead` instead of taking down every worker in turn. An expired lease is reclaimable. `complete`, `fail` and `heartbeat` report a lost lease instead of overwriting the new holder's state. Delivery is at-least-once, so handlers must be idempotent.
  - **Retry and dead-letter:** exponential backoff from 30 s, capped at 1 h, with ±10 % jitter; `PermanentJobError` goes straight to `dead`; `retry_dead`, `prune` (done after 7 days, dead after 30), `stats`, `list` and `next_run_after` cover operations.
  - **A worker only claims types it has a handler for,** so an older build leaves newer job types queued instead of failing them.
  - **Dedupe:** one row per `dedupe_key`. A queued or failed job is refreshed; a running, done or dead one is left alone. `MemoryStore` now enqueues its embed job through `JobQueue.enqueue`, so exactly one place writes `jobs` rows.
  - **`last_error` holds only the exception type and a first line capped at 200 characters,** and the worker logs job id and type, never the payload.
  - Priority: a lower number runs first (0 is most urgent, 5 is the default).
- **EM-208: entities, aliases, relations, and the entity linker.** `em/store/entities.py` adds `EntityStore` (entities, aliases, memory links, relations, `entity_card`) and `em/formation/entity_linker.py` adds `EntityLinker.link(memory)` plus `time_link` for the benchmark.
  - **A capitalised phrase is only promoted to an entity on its second sighting, in a different memory.** One mention is a capitalised word, not an entity. The sighting counter lives in `meta` as a bounded list of distinct memory ids, so the decision survives a restart, is shared by every writer, and one memory mentioning a phrase five times still counts once. Without the threshold the graph fills with entity spam within a week.
  - **A registered entity links on first sighting.** The two-sighting rule only applies to *proposals*; something already in the graph is matched immediately.
  - **Alias lookup is n-gram (1–4 tokens), casefolded, punctuation stripped.** A short name, a two-word name and the same two-word name in shout case with a trailing comma all resolve to the same entity, and a 4-gram claims a mention before a 1-gram can, so a two-word name is not also linked as its own first word.
  - **Query text can never become a lookup key that scans.** `find_entity` is a single indexed probe on the normalised key; the n-gram list is built in memory.
  - **The built-in seed is off by default** (`entities.seed_builtin` is false, and the typed config is EM-407, so it is a parameter). Only the generic list from `triple_extract` is seeded, never anything user-specific.
  - **`entity_card` shows recently closed relations too**, because "used to work on X" is often the most useful line on a card, and it excludes memories whose status is `deleted`.

- **EM-207: episodes and transcript chunks.** `em/store/episodes.py` adds `EpisodeStore` with `upsert_chunks`, `add_episode`, `upsert_episode`, `get_episode`, `list_episodes`, `search_episodes`, `prune_chunks` and `prune_episodes`.
  - **Chunks are content-addressed, which is what makes retries safe.** `transcript_chunks` is keyed by `sha256(session_id, seq, role, text)`, so re-running `upsert_chunks` with the same messages inserts nothing and returns 0 — the AC holds because the primary key is the content, not a counter. `seq` is part of the digest so a sentence repeated within one session stays two chunks.
  - **`add_episode` requires an explicit `session_id` for every kind except `manual`.** It used to default the session key to the new episode's own id, which made every episode its own `window_seq` 0 and silently destroyed window ordering. A manual episode still uses its own id, as the plan specifies.
  - **`upsert_episode` is a separate method** for the case where the caller knows which `(session_id, kind, window_seq)` it is filling and wants a retry to converge rather than raise. `add_episode` is a plain insert, so a duplicate attempt fails loudly instead of overwriting a window.
  - **`search_episodes` cannot be made to execute FTS syntax.** Query tokens are reduced to alphanumerics and quoted, and a query with no usable tokens falls back to a `LIKE` scan, so `" OR "x`, `NEAR(a b)` and `col:val` are searched for literally rather than parsed.
  - **`prune_chunks` keeps a session's chunks while *any* of its episodes is unsummarised.** Testing only the newest episode would let a summarised first window mask an unsummarised third one, and the summariser would be starved of exactly the transcript it still needs. Pending-ness is inferred from an empty summary because the v3 `episodes` table has no status column.
  - Retention window defaults to the plan's `privacy.transcript_retention_days` of 30. The typed config module is EM-407, so it is a parameter with that default rather than a config read here.
- **EM-205: the v3 memories repository.** `em/store/memories.py` adds `MemoryStore` with `add`, `update`, `supersede`, `set_status`, `get`, `list`, `history`, `touch` and `purge`, plus `em/store/types.py` for `Scope`, `MemoryDraft`, `MemoryPatch`, `WriteResult` and the §3.4 status machine. `InvalidTransition` refuses every edge the plan's diagram does not draw, and also refuses a legal edge with the wrong reason code.

  - **Dedup is a query, not a caught constraint violation.** `ux_mem_hash_scope` is a *partial* unique index (`WHERE status IN ('active','pending')`), so superseded and deleted rows are exempt and the same content may legitimately be re-added. Leaning on `IntegrityError` would have permanently blocked re-adding anything that had once been superseded. `add` and `update` both query the hash under the same `WHERE` clause.

- **EM-206: the v3 audit log is now hash-chained, verifiable, and readable from the CLI.** `em/store/audit.py` adds `append()` (called inside the caller's transaction, so a row and the change it describes commit together), `verify() -> VerifyResult(ok, first_bad_seq)` and the frozen digest `sha256(prev_hash || ts || action || actor || target_id || detail)`. The formula is duplicated from migration `0002` on purpose: that migration verifies the chain it rebuilt, so importing a shared helper would let a later edit silently invalidate a historical database. `detail` is stored canonically (`sort_keys`, no whitespace) so key order cannot change a digest, and any value longer than 128 chars is rejected, which is what keeps a fact body or transcript chunk out of the log.
  - New CLI: `entropicmem audit verify` prints `{"ok": true, "checked": N}` and exits non-zero with `first_bad_seq` on a break. The existing `entropicmem audit` listing is unchanged. The command reads the chain directly rather than through the v2 engine, because the v2 `audit_log` is unchained and would have reported OK on a tampered v3 store.
  - Verified against real data: a copy of the live 2.8.0 database migrates to 7168 chained rows and `verify()` confirms every one.
  - **Known limitation, now pinned by a test:** deleting a middle row *and* re-chaining the tail produces a chain that is internally consistent, so no adjacency check can detect it. Seq contiguity is not available as a defence either, because `0002` deliberately preserves the original v2 ids in `seq`. - **EM-204: migration `0002_v3_core` — the v3 schema and the lossless move of every v2 row into it.** Creates the v3 tables (`memories`, `relations`, `entities`, `episodes`, `jobs`, `audit_log`, `meta`, plus external-content `memories_fts`/`episodes_fts` with their sync triggers), renames each v2 source table to `v2_<name>` and keeps it for one release, then copies the data across with new type-prefixed ULIDs while remembering the old id in `legacy_id`. The original ids stay readable: the migration never commits, and a fresh v2 store ends up on `user_version=2` with all v3 tables.
- **EM-204: in-migration parity verification that aborts rather than migrates quietly.** After the data move the migration re-derives expected counts from the renamed v2 tables and compares them per table; it also recomputes `content_hash` for every moved memory, recomputes the audit chain hash for every row, and probes both FTS indexes. Any mismatch raises `ParityError` inside the migration transaction, so the runner rolls the whole thing back and the database stays at its previous version. Seven independent mutations (drop a row, corrupt content, break the chain, drop an FTS trigger, skip dedup, skip episodes, tamper a stored audit row) were each confirmed to be caught, rather than assumed to be.
- **EM-204: v2 rows that v3 cannot represent are preserved, not dropped.** Orphaned `embeddings` and `fact_versions` rows (rows whose parent no longer exists — the real store has 6 and 40) stay in the `v2_*` tables and their counts are recorded in `meta` as `orphans_*`, so the parity arithmetic still balances to the exact v2 row count. Nothing is deleted and nothing dangles under `foreign_keys=ON`.
- **EM-204: rich synthetic v2 fixture builder** (`tests/fixtures/db/build_rich_v2.py`). - **EM-203: migration framework — `em/store/migrations/`.** Each migration is a module named `NNNN_<slug>.py` exposing `VERSION: int`, `NAME: str` and `def up(conn)`. `discover()` loads every numbered module in version order and rejects malformed modules, duplicate versions and gaps in the numbering (migrations must be contiguous from 1, otherwise `user_version` stops meaning "everything up to N has been applied"). `migrate()` backs the database up first via the SQLite backup API to `backups/pre-migrate-v{from}-to-{to}-<ts>.db` (0600, consistent even with a live WAL), then applies each pending migration in its **own** transaction together with its `schema_migrations` row and the `PRAGMA user_version` bump, so a failure mid-migration leaves the database exactly at the last good version. Re-running is a no-op and writes no extra backup; a partially migrated database resumes at the next version instead of re-applying. A database newer than the build raises `DowngradeError`. Editing an already-applied migration raises `MigrationChecksumMismatch` (the recorded `checksum` is `sha256` of the module source) rather than being silently treated as applied.
- **EM-203: development safety guard — migrations refuse to touch a live database.** `assert_safe_db_path()` resolves the path (so `.../entropicmem/../entropicmem/memory.db` cannot dodge the check) and raises `MigrationRefused` for anything outside a temporary or test location; `~/.hermes/entropicmem` and `~/.hermes/entropicmem-live-2.8.0` are denied outright. In-memory databases are always allowed. `migrate()` runs the guard *before* opening a backup or writing anything, so a refused database is not touched at all. The real 3.0 cutover opts in with `ENTROPICMEM_ALLOW_LIVE_MIGRATION=1`, which nothing in development or CI sets.
- **EM-203: migration `0001_baseline_v27`** — the frozen copy of v2's `MemoryEngine._init_schema()` that brings any v2.x store (or an empty database) to the exact v2.7 shape. Every statement is `IF NOT EXISTS` or guarded by a `PRAGMA table_info` check, so it is idempotent across v2.3/v2.5/v2.7/v2.8. `up()` never commits (the runner owns transaction boundaries; `executescript` is deliberately avoided because it issues an implicit COMMIT that would break atomicity). Faithfulness was verified against the real historical engines rather than by reading source: `embeddings` is created unconditionally (v2 gated it on optional deps, but EM-204 moves its rows), `facts_archive` is only *upgraded*, never invented, and `SHARED_SCHEMA` is excluded because it belongs to the separate shared store.
- **EM-203: committed v2.x migration fixtures** (`tests/fixtures/db/v2_{3,5,7}_0.db`) plus `generate_fixtures.py`, which extracts each release commit with `git archive` and runs that release's **real** `MemoryEngine` against a fresh database. - **EM-202: portable storage core — `em/store/` (`db.py`, `locking.py`).** `open_db()` is the single connection factory for the v3 core: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`, `temp_store=MEMORY`, `mmap_size=64MiB`, `isolation_level=None` (explicit transactions only), readonly connections via the SQLite URI `mode=ro`, POSIX perms 0600 file / 0700 dir. `write_txn()` is a `BEGIN IMMEDIATE` … `COMMIT`/`ROLLBACK` context manager with up to 3 jittered retries on SQLITE_BUSY — **no advisory file locks**: cross-process serialisation is SQLite's (BEGIN IMMEDIATE + busy_timeout), proven by the card's concurrency AC (4 writer processes × 500 writes + 1 reader: zero errors, all 2000 rows, reader p95 < 50 ms). `migration_lock()` guards what SQLite cannot see: an `O_CREAT|O_EXCL` lock file (portable, no fcntl/msvcrt), stale after 10 minutes. `ensure_schema()` implements the `PRAGMA user_version` fast path (== LATEST skips all DDL) and refuses DBs newer than the code (`DowngradeError`). `Store` keeps per-thread reader connections (`threading.local`) and ONE process-wide writer serialised by a `threading.Lock`. Stdlib-only, no Hermes imports, no env reads.

### Security

- **CLI `ingest` re-validates every redirect hop (SSRF via redirect).** `validate_url` checked only the first URL, and `urllib` then followed redirects on its own, so a public page answering `302` to `http://169.254.169.254/` (cloud metadata) or a loopback port reached it anyway. A drift-guard test fails if `urlopen` is used directly again. Reported in the Hermes catalog review of 2.8.0 (NousResearch/hermes-agent#122476). Mutation-checked: without the per-hop check, the metadata and loopback redirects both go through.
- **Vector embeddings are opt-in: no model is downloaded unless you enable them.** With `sentence-transformers` importable in the host venv, `remember` built `SentenceTransformer("all-MiniLM-L6-v2")` with no config gate, so the first write downloaded a model from Hugging Face (network egress from a plugin disclosed as local-only). `embeddings.get_embedder()`, the one place a model is built, now requires an explicit opt-in: `embeddings_enabled: true` in the provider config (default `false`), or `ENTROPICMEM_EMBEDDINGS=1` for the CLI. `remember`, `recall_hybrid`, `rebuild_embeddings` and `embedding_stats` all honour it. ## [2.7.0] - 2026-09-22

Hardening release. The engine moved into the plugin directory and every content-trust surface (writes, retrieval, prefetch, the graph viewer, the graph server) got explicit policy.

### Security

- **Write policy** blocks secret and credential content. High-confidence `api_key` / `password` findings are auto-redacted before storage; other PII types are recorded as warn-only findings.
- **Local prompt-injection screen** runs on vault retrieval and on prefetch, `recall`, and `get` tool payloads. Flagged content keeps its place and payload but ships prefixed with a prominent warning marker. Flag-with-warning and fail-open by design: if the screen itself fails, text ships unmarked rather than breaking retrieval.
- **Vault path containment** is enforced on vault writes, so writes cannot escape the resolved vault root.
- **Graph viewer markdown is sanitized** against stored XSS. Output from the markdown renderer and lazy-fetched note bodies both pass a client-side sanitize pass before touching the DOM.
- **Graph server loopback enforcement.** A non-loopback bind is refused at startup unless `ENTROPICMEM_GRAPH_EXPOSE=1` explicitly opts in. When not loopback-bound, the body-bearing read endpoints require `ENTROPICMEM_GRAPH_TOKEN` via the `X-EntropicMem-Token` header; loopback stays tokenless as the local trust plane.
- **Destructive operations gated.** `forget` and `consolidate` require `--confirm` and auto-backup before running; `consolidate` defaults to dry-run.
- **Append-only audit log** records every write.

### Changed

- **Engine relocation.** All engine code now lives under `plugins/entropicmem/scripts/` (previously `skills/entropicmem/scripts/`), making the plugin directory self-contained for catalog installs (`hermes plugins install entropicmem`). The skill `skills/entropicmem/` now holds only `SKILL.md`, `SETUP.md`, and `references/` plus vault templates. CLI invocations use `python3 ~/.hermes/plugins/entropicmem/scripts/entropicmem.py`.
- **Test suite and CI.** 600+ tests on Python 3.10 to 3.12 with pytest pinned in CI. The recall benchmark floor (`precision@5 >= 0.50`, `MRR >= 0.50`) is asserted in CI, and `hermes plugins validate --install-deps plugins/entropicmem` runs as the catalog admission gate.

### Added

- **Lifecycle hooks (5 total).** `on_memory_write` mirrors built-in `memory` tool writes into the engine (primary agent context only). `on_session_switch` tracks session identity and resets per-session caches. `on_session_end` writes an extractive session digest episode (deterministic id, re-firing replaces instead of duplicating) and runs quarantine-first fact extraction into `pending_facts`. `on_turn_start` flushes a partial digest every `turn_cadence_flush_turns` turns for always-on sessions, at most once per `turn_cadence_min_interval_sec`. `on_pre_compress` returns a standing-constraints bullet list to the compression summary prompt and durably checkpoints it as an episode (checkpoint API v2 fail-closed semantics: a non-empty return guarantees the checkpoint is persisted).
